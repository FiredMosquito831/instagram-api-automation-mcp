# Official API automates most surfaces, not follows

Meta's official Instagram Platform API can automate most of the surfaces you listed, but it cannot fully control Instagram. Profile fields and captions are read-only, and none of the pages the notes could reach documents a follow or unfollow endpoint, a conclusion the notes draw from absence rather than from a "not supported" sentence ([IG User reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user)) [fetch summary]. Publishing, comment moderation, mentions, insights and direct messages are documented for professional accounts, and likes and unlikes became official on **April 22, 2026** ([Changelog](https://developers.facebook.com/documentation/instagram-platform/changelog)) [fetch summary]. Three limits shape any CLI. Direct-message replies are allowed only within **24 hours** of the user's message, with a human-agent tag reaching **7 days** and one private reply per comment as the only other documented routes ([Messaging API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api)) [verified]. The publishing cap reads **100** posts per 24 hours on one page and **50** on another ([Content Publishing](https://developers.facebook.com/documentation/instagram-platform/content-publishing)) [verified; fetch summary], and more than **50 like requests in 5 seconds** locks the user out for an hour ([Likes reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/user-likes)) [fetch summary]. Policy is the second constraint: Meta's verified rules bar credential collection, reverse engineering and high-frequency bots in messaging ([Developer Policies](https://developers.facebook.com/devpolicy/)) [verified], and the policy note places bulk or automated likes, follows and unfollows in the prohibited tier, though its sourcing for likes and follows is the thinnest in the set [unverified judgment]. The notes recommend an ESM Node CLI on the official Graph API, starting with Instagram Login, and whether to stay official is a decision only you can make.

**Reading the labels.** Each factual claim carries one of three tags. *Verified* means the notes took the text from a Meta or library page itself: a Context7 copy they describe as near-verbatim, a policy page the policy note tags as read directly, or registry and GitHub metadata they read as API responses. *Fetch summary* means a WebFetch result, which the notes describe as a model-written paraphrase whose quotes need checking on the live page. *Unverified* means a search snippet, a vendor or secondary source, a page the notes never opened, or an inference the notes flag. Where the notes name no method for a page, this report uses the weaker tag. Context7 copies are snapshots, and the surface matrix treats its own Context7 excerpts as unfetched, so check those on the live page before code depends on them.

Every documented surface assumes a professional account. The overview says app users "must have an Instagram professional account" ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [verified], and media owned by personal accounts cannot be read at all ([IG Media reference](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media)) [fetch summary]. Instagram Login uses Business Login for Instagram on the `graph.instagram.com` host and needs no Facebook Page, for accounts "with a presence on Instagram only" ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [verified]. Facebook Login for Business uses `graph.facebook.com`, requires a linked Page, and needs a user who can perform admin-equivalent tasks on that Page ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [verified]. Meta's pages do not recommend either product for new integrations, since the overview's "Recommended use" row names only existing integrations ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [fetch summary]. The notes found no eligibility rule beyond "professional account," and no page states how Creator and Business accounts differ for any feature [unverified].

Profile edits fail on two counts. The IG User reference marks its creating, updating and deleting sections "This operation is not supported," and the 2025 to 2026 changelog has no profile-edit entry ([IG User reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user)) [fetch summary]. The Context7 copy agrees on the readable fields but omits the updating section, so the no-edit claim rests on the summary ([IG User reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user)) [verified for the field list only]. Follows are the sharper gap. The 19-edge IG User list, the documentation index and the 2025 to 2026 changelog contain no follow or unfollow edge ([IG User reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user); [Documentation index](https://developers.facebook.com/documentation/instagram-platform/llms.txt)) [fetch summary]. The nearest official data are an aggregate `follows_and_unfollows` insights count ([IG User insights](https://developers.facebook.com/documentation/instagram-platform/api-reference/instagram-user/insights)) [fetch summary] and two read-only messaging flags, `is_user_follow_business` and `is_business_follow_user` ([Messaging user profile](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api/user-profile)) [verified].

Likes are the newest write action. `POST` and `DELETE /<IG_USER_ID>/likes` take a `media_id` or a `comment_id`, require `instagram_manage_engagement`, and return `{"success": true}` ([Likes reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/user-likes); [Changelog](https://developers.facebook.com/documentation/instagram-platform/changelog)) [fetch summary]. The notes do not say which login product they need. The reference lists `instagram_basic` alongside the new scope, while the changelog says the new scope "is required" ([Likes reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/user-likes)) [fetch summary]. The notes infer that older guidance saying Instagram has no like API is out of date ([Likes reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/user-likes)) [unverified inference]. Deletion is the other messy write path. Post deletion through `DELETE /<IG_MEDIA_ID>` is documented for Facebook Login only, and the same page's request syntax says POST ([IG Media reference](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media)) [fetch summary]. Comment deletion is limited to the media owner, yet the delete section names the comment creator's token ([IG Comment reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-comment)) [fetch summary].

The publishing cap is the number a CLI most needs, and the sources disagree on it. The rate-limit text says accounts "are limited to 100 API-published posts within a 24-hour moving period," enforced on `media_publish` ([Content Publishing](https://developers.facebook.com/documentation/instagram-platform/content-publishing)) [verified]. A carousel passage on the same page says **50** ([Content Publishing](https://developers.facebook.com/documentation/instagram-platform/content-publishing)) [fetch summary], and the quota reference says `quota_total` is "currently 50" ([content_publishing_limit reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/content_publishing_limit)) [verified]. No page says which value is enforced. The notes therefore recommend reading `config.quota_total` from `GET /<IG_ID>/content_publishing_limit` before each publish ([content_publishing_limit reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/content_publishing_limit)) [verified for the endpoint; the pre-publish read is the notes' recommendation]. Story publishing uses a video `STORIES` container, and the notes did not confirm an image path ([Content Publishing](https://developers.facebook.com/documentation/instagram-platform/content-publishing)) [fetch summary].

Owner-only use is the cheapest path, and the notes flag one conflict on it. The App Review table lists an app "only for a business I own or manage" on Instagram Login as Standard Access with App Review "Not required" ([App Review](https://developers.facebook.com/documentation/instagram-platform/app-review)) [verified]. A tutorial sentence says "Instagram requires successful completion of the App Review process before your app can access live data" ([Create an Instagram app](https://developers.facebook.com/documentation/instagram-platform/create-an-instagram-app)) [fetch summary]. New apps start in Development mode, where they "can only request permissions from role users" ([App modes](https://developers.facebook.com/docs/development/build-and-test/app-modes)) [verified]. A Tech Provider serving several businesses needs Advanced Access and App Review ([App Review](https://developers.facebook.com/documentation/instagram-platform/app-review)) [verified]. Advanced Access requires Business Verification, though apps used only by people with app roles do not need it ([Business verification](https://developers.facebook.com/docs/development/release/business-verification)) [fetch summary]. Most apps can have **50 testers**, and the notes found no Instagram-specific cap ([App roles](https://developers.facebook.com/docs/development/build-and-test/app-roles)) [fetch summary].

## Direct messages allow replies only inside a 24-hour window

Messaging on Instagram Login needs a Business or Creator account, an Instagram User token, and the scopes `instagram_business_basic` and `instagram_business_manage_messages` ([Messaging API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api)) [verified]. A CLI lists threads with `GET /<IG_ID>/conversations`, where `platform=instagram` is required, reads a thread with `GET /<CONVERSATION_ID>?fields=messages`, and sends with `POST /<IG_ID>/messages` ([Conversations API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/conversations-api)) [verified]. The recipient is the Instagram-scoped ID (IGSID), which the docs say arrives in a messaging webhook notification, not a username ([Messaging API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api)) [verified]. The list endpoints document no cursor, `limit` or `since` filter, and their sample responses carry no paging object ([Conversations API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/conversations-api)) [fetch summary]. Message details reach only the **20 most recent messages** in a thread, and older ones return an error ([Conversations API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/conversations-api)) [verified].

A reply is allowed for 24 hours, since "Your app has 24 hours to respond to any message sent from an Instagram user" ([Messaging API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api)) [verified]. A first message after a Click-to-Direct ad can extend the window to 7 days ([Messaging API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api)) [fetch summary]. The human-agent tag reaches 7 days from the user's message, but only for human-staffed support ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [verified], and the notes did not find its request syntax [unverified]. A private reply to a comment is the other route. It allows one message within 7 days of the comment, and follow-ups only if the commenter responds, within 24 hours of that response ([Private Replies](https://developers.facebook.com/documentation/instagram-platform/private-replies)) [verified]. For Instagram Live, private replies work only during the broadcast ([Private Replies](https://developers.facebook.com/documentation/instagram-platform/private-replies)) [verified].

Two consequences follow. The CLI cannot open a thread with someone who has never messaged the account, and group threads are not supported ([Messaging API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api)) [verified]. The private reply is the only documented route to a first message, which the notes infer from the listed options [unverified inference]. The human-agent clock and the private-reply clock run separately, so a CLI should store both timestamps per thread [unverified inference].

Inbound messages arrive by webhook. The notes give the subscription as a `POST` to the account's `subscribed_apps` edge with `subscribed_fields` ([Webhooks setup](https://developers.facebook.com/documentation/instagram-platform/webhooks/setup)) [fetch summary]. Meta verifies the endpoint with a GET carrying `hub.mode`, `hub.challenge` and `hub.verify_token`, and expects the challenge echoed back ([Webhooks setup](https://developers.facebook.com/documentation/instagram-platform/webhooks/setup)) [fetch summary]. Each notification carries an `X-Hub-Signature-256` header, "preceded with sha256=," computed over the payload with the app secret ([Webhooks](https://developers.facebook.com/documentation/instagram-platform/webhooks)) [verified]. The docs do not say whether the digest is HMAC or how it is encoded, so a CLI must confirm the scheme on a real payload [unverified]. Failed deliveries are retried over 36 hours, batches can hold up to 1,000 updates, and duplicates are possible, so the endpoint must deduplicate ([Webhooks setup](https://developers.facebook.com/documentation/instagram-platform/webhooks/setup)) [fetch summary]. Webhook history cannot be queried ([Webhooks](https://developers.facebook.com/documentation/instagram-platform/webhooks)) [verified], and the endpoint needs a valid TLS certificate, because self-signed certificates are not supported ([Webhooks](https://developers.facebook.com/documentation/instagram-platform/webhooks)) [verified]. The notes name no tunnel or local-development tool [unverified].

Polling is the fallback. The conversation list returns `updated_time`, the time of the most recent message, so a poller can re-read only changed threads ([Conversations API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/conversations-api)) [verified]. The notes call that workable but not an official pattern [unverified inference], and the endpoint is capped at **2 calls per second** per professional account ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [verified]. Sends are capped at **100 calls per second** for text, links, reactions and stickers, and **10** for audio or video ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [verified]. Text and links are limited to 1,000 bytes, and up to ten images can go in one message, out of beta on May 6, 2026 ([Messaging API](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/messaging-api)) [verified for the limits; the date comes from the changelog summary]. The notes found no per-hour or per-day DM send limit, but did not confirm that none exists [unverified]. Story replies arrive as messaging payloads with `reply_to.story` ([Changelog](https://developers.facebook.com/documentation/instagram-platform/changelog)) [fetch summary].

## Unofficial tools cluster where the policy risk is highest

The rules the notes could verify come from the Meta Platform Terms and Developer Policies, both last updated February 3, 2026 ([Meta Platform Terms](https://developers.facebook.com/terms/); [Developer Policies](https://developers.facebook.com/devpolicy/)) [verified]. Apps may not "separately request or collect a Meta user's login credentials" ([Meta Platform Terms](https://developers.facebook.com/terms/)) [verified], may not reverse engineer "Platform or any aspect thereof" ([Meta Platform Terms](https://developers.facebook.com/terms/)) [verified], and may not maintain apps "to circumvent, or attempt to circumvent, our enforcement actions" ([Meta Platform Terms](https://developers.facebook.com/terms/)) [verified]. The Developer Policies bar bots run "at very high frequencies," spam and "inauthentic behavior" in Instagram Messaging, and any action "on their behalf" taken without consent ([Developer Policies](https://developers.facebook.com/devpolicy/)) [verified]. Experiences with excessive negative feedback "may be feature limited, paused, rate-limited or removed" ([Developer Policies](https://developers.facebook.com/devpolicy/)) [verified].

The rules most relevant to likes and follows are the ones the notes could not read. The Instagram Terms pages returned only the words "Help Center," so the automated-access clause is known only from a search summary ([Instagram Terms](https://help.instagram.com/581066165581870/)) [unverified]. The Community Standards spam and inauthentic-behavior pages returned titles only ([Spam](https://transparency.meta.com/policies/community-standards/spam/); [Inauthentic Behavior](https://transparency.meta.com/policies/community-standards/inauthentic-behavior/)) [unverified]. The robots.txt notice was not fetched ([robots.txt](https://www.instagram.com/robots.txt/)) [unverified]. The notes found no Meta page on private or undocumented API use, and no rule that names like or follow actions specifically [unverified absence].

The only statements on likes and follows are secondhand. A search summary of a VentureBeat article says Instagram calls trading likes, shares, comments or followers "long been off-limits," and that it will keep enforcing its API terms. The notes could not date the article ([VentureBeat](https://venturebeat.com/social/new-third-party-instagram-apps-cant-follow-or-like-on-users-behalf/)) [unverified]. A Gulf News report on a plan to purge artificial engagement from third-party tools is dated 2018 only by its URL ([Gulf News](https://gulfnews.com/amp/technology/instagram-to-target-fake-followers-likes-1.1542673331252)) [unverified]. Help Center summaries name giving login details to apps that promise likes or followers as a trigger for review ([Help Center](https://help.instagram.com/740480200552298/)) [unverified].

Enforcement terms are broad. The Platform Terms let Meta suspend or terminate apps or accounts "in our sole discretion," with or without notice ([Meta Platform Terms](https://developers.facebook.com/terms/)) [verified]. The notes found no primary Meta page on action blocks, checkpoints, disablement timelines or appeals [unverified absence]. Vendor claims about 2026 bans, such as 24 to 72 hour bans for unofficial tools, are unsourced ([ReplyRush](https://www.replyrush.com/post/is-instagram-dm-automation-safe-1); [PilotDM](https://www.pilotdm.com/blog/instagram-account-ban-2026-what-is-happening-and-how-to-stay-safe)) [unverified], and vendors selling automation have an interest in that framing. A TechCrunch item, dated by its URL to December 6, 2024, reports a Meta change that limited third-party consumer apps' Instagram data access. The notes read only its title and URL ([TechCrunch](https://techcrunch.com/2024/12/06/instagram-locks-out-developers-of-third-party-consumer-apps)) [unverified].

The policy note sorts the likely actions into three tiers. The tiers are its own judgment, built on the verified rules above, and it marks the line for automated replies as unclear, because the rule gives no numeric threshold for "very high frequencies" ([Developer Policies](https://developers.facebook.com/devpolicy/)) [verified for the rule; the threshold gap is unverified].

## Commander and native fetch make a small ESM CLI

The stack note recommends the layers below. Versions and dates come from `npm view` on the registry, and library behaviour comes from Context7 excerpts, so both are verified. The npm docs came through WebFetch. The notes do not say how the Node.js pages were read, so this report treats them as paraphrase.

The stack is ESM JavaScript, which matches your request for a JavaScript CLI. The inventory note instead suggests a thin TypeScript CLI, a choice covered in the final section.

Business Login is a chain of three tokens. An authorization code lasts one hour and works once. A short-lived Instagram User token lasts one hour. A long-lived token lasts 60 days, from an `ig_exchange_token` call that must run server-side because it carries the app secret ([Business Login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login)) [verified]. A refresh adds 60 days, but only when the token is at least 24 hours old, unexpired, and carries `instagram_business_basic`. A token left unrefreshed for 60 days cannot be refreshed ([Business Login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login)) [verified]. Two gaps matter for a CLI. The docs do not say how the 24-hour age is counted [unverified]. A CLI has no server, so it must hold the app secret locally, and the notes found no CLI-specific guidance [unverified inference]. Lifetimes "may change without warning or expire early" ([Access tokens](https://developers.facebook.com/docs/facebook-login/guides/access-tokens)) [fetch summary]. Expired tokens return error 190 ([Error handling](https://developers.facebook.com/docs/graph-api/guides/error-handling)) [fetch summary]. Whether a password change invalidates Instagram Login tokens is unconfirmed, despite subcode 460 ([Error handling](https://developers.facebook.com/docs/graph-api/guides/error-handling)) [unverified].

Pin `v26.0`. The versioning page calls it the latest and says each version works for at least two years ([Versioning](https://developers.facebook.com/docs/graph-api/guides/versioning)) [fetch summary]. No page confirms the version policy for the `graph.instagram.com` host, so the notes advise one test call before relying on it [unverified]. Instagram calls draw on a budget of **4,800 × impressions per 24 hours** per app and app-user pair, excluding messaging ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [verified]. The notes found no behaviour at zero impressions [unverified]. Usage appears in the `X-Business-Use-Case-Usage` header, but the rate-limit page does not name an Instagram-specific header, and no live response confirmed it [unverified] ([Rate limiting](https://developers.facebook.com/docs/graph-api/overview/rate-limiting)) [fetch summary]. Throttling is triggered when `total_cputime` or `total_time` reaches 100 ([Rate limiting](https://developers.facebook.com/docs/graph-api/overview/rate-limiting)) [fetch summary].

Two deprecations break old code. The Sept 17, 2024 changelog entry replaced the old scope values with `instagram_business_*` names. The old values were deprecated on January 27, 2025, and the changelog warns that failing to migrate leaves the app unable to call the Instagram endpoints ([Changelog](https://developers.facebook.com/documentation/instagram-platform/changelog)) [verified from the Context7 snippet]. The hyphenated v1.0 endpoints are deprecated, so current code uses `<IG_COMMENT_ID>` and `<IG_MEDIA_ID>` paths ([Changelog](https://developers.facebook.com/documentation/instagram-platform/changelog)) [fetch summary]. The changelog also says `media_url` can be absent from **July 30, 2026**, with the HTTP status staying 200, across 13 GET paths including `media`, `stories` and `mentioned_media` ([Changelog](https://developers.facebook.com/documentation/instagram-platform/changelog)) [fetch summary]. That date is before this report, so code should assume the change applies [inference from dates].

On Windows, file permission bits do not restrict other users. Node's file-system docs say only the write bit can be changed and that group, owner and other permissions are not implemented ([Node fs docs](https://nodejs.org/docs/latest-v24.x/api/fs.json)) [fetch summary]. The notes therefore favour the OS credential store over a token file, and infer that Windows default ACLs keep a user-profile file private, which they did not verify [unverified inference]. The notes also infer that `@napi-rs/keyring` uses Credential Manager on Windows, since its README documents only Linux backend selection [unverified inference].

## Build on the official API, and decide how much the gaps matter

The notes support building on the official API rather than an unofficial library, and their evidence makes that the defensible position. The case for going unofficial is coverage. Unofficial libraries and listings advertise likes, follows and DM automation, and instagrapi alone has 6,985 stars ([instagrapi](https://github.com/subzeroid/instagrapi)) [verified]. The case against is that the policy reading places unofficial endpoint use in the gray-to-prohibited range with high enforcement risk, and that no verified Meta text names unofficial endpoints either way ([Developer Policies](https://developers.facebook.com/devpolicy/)) [verified; the risk rating is judgment].

Start with Instagram Login for an owner-only CLI. The notes find publishing, comment moderation, mentions, insights and messaging documented for that product without a Facebook Page ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [verified for the Instagram Login requirements; fetch summary for the feature matrix]. Add Facebook Login and a linked Page only for the features the notes list as Facebook Login only: post deletion, hashtag search, business discovery, product tags and partnership ads ([Overview](https://developers.facebook.com/documentation/instagram-platform/overview)) [fetch summary]. Likes are the open case. Their examples use `graph.facebook.com`, which suggests Facebook Login, but the notes did not confirm it ([Likes reference](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/user-likes)) [unverified inference]. Test likes with each token type before choosing.

Several rules follow from the findings and should be fixed in code. Pin `v26.0`. Read the publishing quota from `config.quota_total` before each publish, read the usage header, and throttle below the like limit of 50 requests in 5 seconds. Use only current endpoint paths and `instagram_business_*` scopes, and handle a missing `media_url`. Send only text the account owner wrote, since the Developer Policies bar pre-filled message text ([Developer Policies](https://developers.facebook.com/devpolicy/)) [verified]. Refuse bulk likes, follows and unfollows, any DM triggered by a follow, and any send outside the 24-hour window or the human-agent and private-reply clocks. Deduplicate webhook deliveries on the message ID, since retries and duplicates make that necessary ([Webhooks setup](https://developers.facebook.com/documentation/instagram-platform/webhooks/setup)) [fetch summary for the retry text; the message-ID rule is an unverified inference]. These are design recommendations drawn from the findings above, not facts from the sources.

The stack follows the Node section above: commander 15.0.0, built-in `fetch` with a retry helper the project owns, `@napi-rs/keyring` for a saved login with the environment variable read first, `node:test`, and a `node:http` receiver for webhooks. A request layer could be `instagram-graph-api-lib` or the notes' own helper. The notes recommend the library but did not read its code, so adopting it is a decision to make after reading it ([instagram-graph-api-lib](https://github.com/TiagoGrosso/instagram-graph-api-lib)) [verified for metadata; code unverified].
